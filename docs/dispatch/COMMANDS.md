# Dispatch commands

Outside the prompt: `dispatch` (start/attach, open dashboard unless `--no-browser`, enter the prompt), **`dispatch --project <folder> [request]`** (use a local folder as the project, no GitHub needed), **`dispatch <request>`** (same, then create a request, e.g. `dispatch add dark mode to settings`; the dashboard opens only if this call started the factory; a one-word near-miss of a subcommand such as `dispatch statu` is refused instead of becoming a request), `start`, `status`, `doctor`, `stop [--yes]`, `migrate [--yes]`, `--help`, `--version`.
(On macOS the program is `dispatch`, not `/dispatch`, which would address the filesystem root.)

Inside the prompt: `/dispatch <request>` (tab completes `/dispatch `), `/help /new /projects /project use <id|owner/name> /jobs /status /models /skills /agents /approvals /approve <id> /pause <id> /resume <id> /cancel <id> /logs <id> /dashboard /context [clear] /exit /shutdown`.

- A request goes to the active project; if none is selected and exactly one project exists it is used; with several you are asked to choose (`/project use`); with none nothing is created. The text is stored verbatim as untrusted data. The job then waits in `QUEUED` until a worker with a qualified, authorized model exists (none does yet).
- A job reference is a full id, a unique id prefix (6+ chars) or a unique title fragment. Anything ambiguous lists the candidates and does nothing.
- `/cancel` and `/approve` ask for a separate typed confirmation that is bound to the revision you were shown; if the job changed meanwhile nothing happens.
- `/runs`, `/review [run]`, `/accept [run]`, `/discard [run]` (agent work: list, show the diff, apply after typing `apply`, reject), `/exit` (or Ctrl-D) detaches and leaves the factory and its jobs running. `/shutdown` stops only services Dispatch started, after warning about in-flight jobs.
- Unknown `/commands` are never sent to a model or a shell; you get suggestions.
- Plain sentences: a fixed set of phrases ("show my jobs", "list models", "status") is matched without any model. Everything else is refused unless a qualified, authorized interpreter is configured (none is). Even then its output is schema-validated and can only *propose*; mutations still need your confirmation.
- **Projects are optional GitHub.** `/new <folder>` (or `/project add <folder>`, or `dispatch --project <folder>`) registers a folder on this machine as a project and makes it active. It is validated by the API: the real path (symlinks resolved) must be a readable folder; the filesystem root, your whole home folder, system folders, credential/app-data folders (`~/.ssh`, `~/.aws`, `~/Library`, …) and Dispatch's own data are refused. Adding the same folder twice is idempotent. **If the folder does not exist, Dispatch asks "Create it? (y/N)" and creates exactly that path only on yes** (relative names such as `MeetingNotes` resolve against the folder you started `dispatch` in; the full path is shown first). The same safety rules apply to a folder that would be created (nothing is created in system, credential or app-data places, or where you lack write permission). Paths may be typed shell-style: `ScribeDeck\ Transcripts` or in quotes. A folder need not be a git repository, but changes to a non-git folder cannot be tracked. `/approve` decides capability approvals for the exact digests shown; job-merge decisions are made in the dashboard because they bind to an exact commit.
- Not persisted: command history (so secrets typed at the prompt are never written to disk). The session scope (active project, remembered ids) is stored 0600 and expires after 8 h.
